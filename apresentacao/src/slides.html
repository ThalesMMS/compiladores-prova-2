Questão 1 · Análise sintática ascendente

Construir o autômato e a tabela em seis passos

Toda questão de LR segue o mesmo roteiro. LR(0) e SLR usam o mesmo autômato; LR(1) acrescenta lookaheads e pode criar mais estados; LALR funde estados LR(1) de mesmo núcleo. As colunas das reduções também dependem do método.

Por extenso: Do texto da gramática à decisão do parser

Em palavras

O parser recebe tokens e precisa decidir: “leio mais um token ou já reconheci uma construção inteira?”. Cada estado reúne itens que descrevem as possibilidades naquele ponto. O autômato mostra como essas possibilidades mudam; a tabela transforma isso em instruções para o parser.

closure significa “inclua também as produções que posso precisar começar agora”. goto(I, X) significa “partindo do estado I, reconheça X, avance os pontos correspondentes e complete o novo conjunto com closure”. Repita até não aparecer nenhum conjunto novo.

Exemplo, passo a passo

Com S → a, o estado inicial contém Start → • S e S → • a. A seta por a chega a S → a •: o a foi reconhecido e pode ser reduzido a S. A seta por S chega a Start → S •: ao encontrar o fim da entrada, aceite.

Na tabela, uma seta por terminal vira deslocamento; por não terminal, Goto. Um item comum terminado autoriza redução nas colunas permitidas pelo método. O item aumentado terminado autoriza aceitação em eof.

Não confunda

O roteiro é comum, mas não muda apenas a tabela: LR(1) acrescenta lookaheads aos itens e pode separar estados; LALR funde estados LR(1) de mesmo núcleo. LR(0) e SLR, por sua vez, usam o mesmo autômato.

A receita

  1. Aumente e numere. Acrescente Start → S (produção 0) e numere as demais: r1, r2, …
  2. Estado inicial. CC₀ = closure({[Start → • S, eof]}).
  3. Demais estados. Para cada estado e cada símbolo X depois de um ponto: CCⱼ = goto(CCᵢ, X). Conjunto novo vira estado novo; repetido reaproveita o existente.
  4. Tabela. Transição por terminal → sN; por não terminal → gN; item completo → rN nas colunas do método; [Start → S •, eof] → acc.
  5. Conflitos. Duas ações na mesma célula ⇒ a gramática não é daquele tipo.
  6. Pilha. Execute a entrada com pares (símbolo, estado): Passo | Pilha | Entrada | Ação.
Algoritmo como no caderno:

No LR(0) e no SLR os itens não têm o “, ℓ”: o closure só acrescenta Y → • δ.

Questão 1 · Fundamentos

O que um item diz, e de onde sai o lookahead

Um item LR(1) [A → B • C f, a] lê-se: “já reconheci B; ainda faltam C f; quando a produção inteira terminar, o próximo token pode ser a”.

Por extenso: O ponto é progresso; o lookahead é contexto

Em palavras

Leia [A → B • C f, a] assim: “nesta possibilidade, B já foi reconhecido; ainda preciso reconhecer C e depois f; quando toda a produção de A terminar, o próximo token poderá ser a”. O a depois da vírgula não faz parte da produção.

Se o ponto está antes de Y, preciso abrir as possibilidades de Y. Para saber em que contexto Y pode terminar, olho o que vem depois dele: a sequência β e, caso ela possa desaparecer, o lookahead ℓ do item original. É isso que FIRST(β ℓ) calcula.

Exemplo, passo a passo

Em [A → B • C f, a], depois de C vem f. Logo, ao abrir C → c, acrescento [C → • c, f]. Em [A → B • C, a], não há nada depois de C; acrescento [C → • c, a]. Se os dois itens estão no estado, aparecem os dois lookaheads: {a, f}.

Se β fosse um não terminal que produz c ou ε, os lookaheads incluiriam c e ℓ. Ser anulável não apaga as outras possibilidades de FIRST.

Não confunda

closure não consome entrada e não avança o ponto do item que já existe. goto avança todos os itens que têm X logo após o ponto, não apenas um deles; depois aplica closure ao resultado.

A regra do lookahead

Se um item tem o ponto antes de um não terminal Y:

[X → α • Y β, ℓ] ⇒ [Y → • δ, s] para cada s ∈ FIRST(β ℓ)

Em palavras: o que pode aparecer depois do Y é o começo de β; se β pode sumir (ou não existe), é o próprio ℓ.

  • [S → • A a, eof]: depois de A vem a ⇒ FIRST(a eof) = {a}.
  • [A → • B C f, a]: depois de B vem C f ⇒ FIRST(C f a) = FIRST(C) = {c}.
  • [A → B • C, a]: depois de C não vem nada ⇒ FIRST(a) = {a}.

goto avança todos os itens

goto(CC₀, B) pega os dois itens com B depois do ponto, [A → • B C, a] e [A → • B C f, a], e avança os dois. Esquecer um deles é o erro mais comum.

Itens iguais em produção e ponto, mas com lookaheads diferentes, costumam ser escritos juntos: [C → • c, {a, f}].

Questão 1 · Comparando os métodos

Mesmo procedimento, reduções em colunas diferentes

Por extenso: Quatro maneiras de decidir quando reduzir

Em palavras

Uma redução diz: “o trecho que reconheci pode ser substituído pelo não terminal da produção”. A diferença central entre os métodos é a precisão da informação usada para autorizar essa substituição.

LR(0) autoriza a redução comum em todos os terminais. SLR restringe a FOLLOW do não terminal. LR(1) usa o lookahead daquele item, naquele contexto. LALR compacta estados LR(1) com o mesmo núcleo e reúne seus lookaheads.

Exemplo, passo a passo

Imagine o estado com [A → B C •, a] e [A → B C • f, a]. Com próximo token a, reduza B C a A. Com f, ainda complete a alternativa B C f. LR(1) separa as decisões por coluna; LR(0) também colocaria a redução na coluna f, criando conflito.

Não confunda

Conflito não é “duas ações na linha”: é “duas ações diferentes na mesma célula”. Um estado pode reunir alternativas sem ser ambíguo para o parser.

O item aumentado completo é especial: gera aceitação só em eof. Não é uma redução comum ocupando toda a linha. Ao fundir uma coleção LR(1) sem conflitos, LALR pode introduzir reduce/reduce, mas não um novo shift/reduce.

Conflitos

  • shift/reduce: na mesma célula, deslocar ou reduzir.
  • reduce/reduce: na mesma célula, reduzir por duas produções.

Ter item completo e item de deslocamento no mesmo estado não é conflito por si só: só é se as ações caírem na mesma coluna.

Como classificar rápido

  1. Monte o LR(0). Sem conflitos? É LR(0) — e portanto SLR, LALR e LR(1).
  2. Com conflito, use FOLLOW (SLR). Sumiu? É SLR.
  3. Ainda há conflito: monte o LR(1). Sem conflito? É LR(1).
  4. Funda estados LR(1) de mesmo núcleo. Sem conflito? É LALR.

LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ LR(1)

A fusão LALR nunca cria shift/reduce novo; só reduce/reduce.

Questão 1 · Exemplo resolvido em aula

Cmd → Lhs = Rhs | Rhs: o LR(1) completo do quadro

É a gramática das atribuições com ponteiro (id = **id). A numeração CC₀…CC₁₃ e a tabela coincidem com o caderno, e a aba Pilha refaz os 13 passos do quadro.

Por extenso: Como o parser reconhece id = **id

Em palavras

A gramática distingue um lado esquerdo, Lhs, de uma expressão à direita, Rhs. Aqui * Rhs é a forma de indireção com ponteiro; esse asterisco não representa uma multiplicação entre dois operandos.

O autômato não executa uma atribuição. Ele verifica se a sequência de tokens pode ser montada pelas produções. Cada redução reconhece uma peça maior a partir das menores que já estão na pilha.

Exemplo, passo a passo

No começo de id = * * id, o primeiro id vira Lhs. Ao ver =, o parser continua a alternativa Cmd → Lhs = Rhs, em vez de encerrar o comando como um Rhs.

Na parte direita, o último id vira Lhs e depois Rhs. O trecho * Rhs vira Lhs e depois Rhs; o processo se repete para o outro asterisco. Finalmente, Lhs = Rhs vira Cmd e o parser aceita em eof.

Não confunda

Dois estados podem ter os mesmos pontos nas mesmas produções e ainda ser diferentes no LR(1), porque os lookaheads são diferentes. A vista “núcleo” ajuda a enxergar a estrutura, mas não substitui a leitura dos lookaheads.

r0: Start → Cmd      r1: Cmd → Lhs = Rhs   r2: Cmd → Rhs
r3: Lhs → * Rhs      r4: Lhs → id         r5: Rhs → Lhs

Repare que CC₄ e CC₁₂ têm os mesmos itens com lookaheads diferentes ({=, eof} contra eof). No LR(1) eles são estados distintos; no LALR, viram um só. O mesmo vale para 5/11, 7/13 e 8/10.

Questão 1 · Exemplo do quadro

O conflito que só o lookahead resolve

Troque o método e veja a célula [2, =] mudar.

Por extenso: Por que FOLLOW pode autorizar uma redução indevida

Em palavras

FOLLOW reúne os tokens que podem vir depois de um não terminal em algum contexto da gramática. Ele não distingue todos os contextos particulares de cada estado. SLR usa esse conjunto global; LR(1) consegue guardar uma informação mais localizada.

No estado que já reconheceu um Lhs no início do comando, = permite continuar uma atribuição. Reduzir esse Lhs a Rhs ali significaria escolher a alternativa de comando formada apenas por um Rhs.

Exemplo, passo a passo

O SLR encontra = em FOLLOW(Rhs) e põe r5 na coluna =. Mas essa célula já tem s6, da continuação Lhs • = Rhs. No LR(1), o item completo é [Rhs → Lhs •, eof]: r5 fica só em eof e = fica só com s6.

Não confunda

A presença de = em FOLLOW(Rhs) não é erro de cálculo. O problema é usar uma informação global num contexto em que ela é ampla demais. Essa gramática continua sem conflitos após a fusão LALR.

SLR: conflito em CC₂

CC₂ = { Cmd → Lhs • = Rhs, Rhs → Lhs • }.

O SLR reduz Rhs → Lhs em FOLLOW(Rhs) = {=, eof}. Mas o primeiro item desloca =: a célula [2, =] fica com s6 / r5.

FOLLOW(Rhs) tem “=” porque Lhs → * Rhs e Cmd → Lhs = Rhs. Só que ali, no começo do comando, um Rhs nunca é seguido de “=”.

LR(1) e LALR: sem conflito

No LR(1) o item é [Rhs → Lhs •, eof]: a redução vai só para eof, e “=” fica com s6.

O LALR funde 4/12, 5/11, 7/13 e 8/10 (10 estados, como o LR(0)) e continua sem conflito.

Resposta: não é LR(0) nem SLR(1); é LALR(1) e LR(1).

Questão 1 · Lista 1 · Exercício 1

CN → CN tick tock | tick tock

Gera uma ou mais repetições de “tick tock”. Use os botões de método para responder (a) a (d).

Por extenso: Por que aceitar não é a mesma coisa que reduzir

Em palavras

A produção CN → tick tock reconhece o primeiro par. CN → CN tick tock acrescenta mais um par a uma sequência já reconhecida. Portanto, a linguagem tem um ou mais pares completos; não permite um tick isolado nem a sequência vazia.

Exemplo, passo a passo

Depois de reconhecer um CN, há duas possibilidades: terminar o programa ou acrescentar outro par. Em eof, o item Start → CN • autoriza aceitar. Em tick, o item CN → CN • tick tock autoriza deslocar.

Para tick tock tick tock, reconheça o primeiro par como CN, leia o segundo e reduza CN tick tock a CN. Depois aceite no fim da entrada.

Não confunda

Não espalhe a aceitação por todas as colunas, nem escreva r0 como redução comum. É justamente por acc ficar em eof e o deslocamento ficar em tick que esses dois itens podem coexistir sem conflito no LR(0).

(a) AFD LR(0)

CC₀ = {Start → • CN, CN → • CN tick tock, CN → • tick tock}. goto(CC₀, CN) avança dois itens: CC₁ = {Start → CN •, CN → CN • tick tock}.

A tabela LR(0) não tem conflito: em CC₁ o item completo é o de aceitação (coluna eof) e o deslocamento é em tick. A gramática é LR(0), ao contrário do que diz o enunciado.

(b) SLR · (c) LR(1) · (d) LALR

(b) FOLLOW(CN) = {tick, eof}: as reduções saem da coluna tock. Continua sem conflito.

(c) Mesmos 6 estados, com lookahead {tick, eof} nos itens de CN.

(d) Nenhum par de estados tem o mesmo núcleo: nada a fundir. LALR = LR(1).

É LR(0), SLR(1), LALR(1) e LR(1).

Questão 1 · Lista 1 · Exercício 2 (a)

A coleção canônica LR(1), um goto de cada vez

Este é o formato da prova: avance os passos e, em cada closure, leia a justificativa de cada lookahead.

Por extenso: De onde vêm c, a e f nos itens do exercício

Em palavras

S → A a diz que A termina antes de a. Por isso as duas alternativas de A recebem lookahead a. Em ambas, o primeiro símbolo a reconhecer é B e depois vem C; como C começa por c, os itens de B recebem lookahead c.

Cada estado novo deve reunir todas as possibilidades que sobrevivem ao mesmo reconhecimento, não uma alternativa isolada escolhida antecipadamente.

Exemplo, passo a passo

Ao reconhecer B, avance tanto A → • B C quanto A → • B C f. Obtenha A → B • C e A → B • C f.

Agora abra C duas vezes: na primeira alternativa, C está no fim e herda a; na segunda, C é seguido por f. O item C → • c fica com os contextos a e f. “c” é o token que C reconhece; “a ou f” são os tokens que podem aparecer depois de C.

Não confunda

Não copie mecanicamente o lookahead do pai para todos os filhos. Primeiro calcule o que pode começar a sequência que está depois do não terminal; só acrescente o lookahead do pai quando essa sequência puder desaparecer.

r0: Start → S    r1: S → A a    r2: A → B C    r3: A → B C f    r4: B → b    r5: C → c

Os dois closures que valem ponto: em CC₀, [B → • b, c] porque depois de B vem C (FIRST(C a) = FIRST(C f a) = {c}). Em CC₃, [C → • c, {a, f}]: a vem de [A → B • C, a] (nada depois de C, sobra o lookahead) e f vem de [A → B • C f, a].

Questão 1 · Lista 1 · Exercício 2 (b) e (c)

Da coleção para a tabela Ações/Goto

Toque em qualquer célula para ver o item que a gerou. A coluna Start não aparece no Goto: a produção aumentada só serve para aceitar.

Por extenso: Lendo uma célula como uma instrução

Em palavras

Leia Ação[i, a] = r2 assim: “se o topo da pilha está no estado i e o próximo token é a, reduza pela produção 2”. Leia s8 como “consuma esse token e vá para o estado 8”. Goto é usado com não terminais, depois de uma redução.

Uma célula vazia não é uma ação esquecida: quando o parser precisa consultá-la, significa que aquela continuação não é aceita.

Exemplo, passo a passo

No estado com A → B C • e A → B C • f, o próximo token resolve a dúvida: a encerra A pela produção curta; f continua a produção longa. No LR(1), a recebe r2 e f recebe s8. No SLR, FOLLOW(A) = {a} também basta para separar essas decisões.

Não confunda

No LR(0), r2 também ocuparia f, disputando a mesma célula com s8. É esse par de ações na célula [6, f], e não apenas a presença de dois itens no estado, que demonstra o conflito.

(c) É LR(1)? Sim.

O único estado com item completo e deslocamento juntos é CC₆:

[A → B C •, a] [A → B C • f, a]

Com lookahead a reduz r2; com f desloca s8. Células diferentes ⇒ sem conflito. A tabela inteira não tem conflitos ⇒ LR(1).

Bônus: e os outros métodos?

No LR(0), r2 ocuparia a linha inteira de CC₆, inclusive a coluna f, onde já há s8: conflito. Então não é LR(0).

No SLR, FOLLOW(A) = {a} resolve: é SLR(1), e também LALR(1).

Questão 1 · Lista 1 · Exercício 2 (d)

Executando o parser com a pilha de pares (símbolo, estado)

A cada passo, consulte Ação[estado do topo, próximo token]. A tabela ao lado acende a célula usada. Experimente também entradas erradas, como b c a a.

Por extenso: Reduzir troca um trecho da pilha, não lê um token

Em palavras

A pilha guarda o que já foi reconhecido e os estados alcançados. O próximo token só é consumido no deslocamento. Na redução, o parser reorganiza o que já estava na pilha.

Se a produção é A → β, retire um par por símbolo de β. O estado que aparecer no topo diz de onde aquele trecho começou. Consulte Goto nesse estado para empilhar A com o estado correto.

Exemplo, passo a passo

Com pilha (⊥,0)(B,3)(C,6)(f,8) e entrada a eof, r3 usa A → B C f. Retire três pares: B, C e f. Resta o estado 0; Goto[0,A] = 2; a pilha passa a (⊥,0)(A,2).

A entrada continua a eof. Só a ação seguinte que deslocar a vai consumir esse token. Assim, vários passos de redução podem acontecer sem a entrada avançar.

Não confunda

Não consulte Goto no estado que acabou de ser retirado. Consulte no topo exposto depois de desempilhar. E conte símbolos da produção, não caracteres do nome: intLit, por exemplo, é um único símbolo.

Deslocamento

sN: empilha (token, N) e consome o token.

Redução

rN com A → β: desempilha |β| pares, olha o estado exposto e empilha (A, Goto[exposto, A]). A entrada não muda.

Notação

O fundo da pilha é (⊥, 0), como no quadro. O gabarito escreve (eof, 0): é o mesmo marcador.

Questão 1 · Lista 1 · Exercício 3

Braço robótico: projetar uma gramática LR(1)

Válida = em todo prefixo, nº de ↓ ≥ nº de ↑. O saldo final pode ser positivo (sobram maçãs).

Por extenso: O saldo precisa ser válido durante todo o percurso

Em palavras

Pense em ↓ como colocar uma maçã e ↑ como retirar uma. Começando com zero, nunca se pode retirar o que ainda não foi colocado. Por isso o saldo precisa ser não negativo em todo prefixo, e não apenas no final.

B representa um trecho balanceado, que termina com o mesmo saldo com que começou. S permite também descidas que nunca serão compensadas: a sequência pode terminar com maçãs sobrando.

Exemplo, passo a passo

↓ ↑ ↓ tem saldos 1, 0 e 1: é válida. ↓ ↑ ↑ ↓ termina com saldo zero, mas seus saldos são 1, 0, −1 e 0: é inválida porque a terceira operação tenta retirar uma maçã inexistente.

Em S → ↓ B ↑ S, a primeira descida é compensada pela subida mostrada; B descreve o que ocorre de forma balanceada entre elas. Em S → ↓ S, aquela primeira descida permanece sem compensação.

Não confunda

ε significa “não produzir nenhum token”. Reduzir B → ε não consome entrada e não retira pares da pilha. O parser apenas consulta Goto no estado que já estava no topo.

(a) A gramática

r0: Goal → S
r1: S → ↓ S          // esta ↓ nunca é retirada
r2: S → ↓ B ↑ S      // ↓ … ↑ casados
r3: S → ε
r4: B → ↓ B ↑ B      // balanceada (saldo 0)
r5: B → ε

B gera as sequências balanceadas; S, todas as válidas. Uma sequência válida começa com ↓: ou essa ↓ nunca é compensada (S → ↓ S), ou é compensada por uma ↑, com um trecho balanceado entre elas (S → ↓ B ↑ S).

(b) Prova de que é LR(1)

FOLLOW(S) = {eof} e FOLLOW(B) = {↑}. A tabela (abaixo) não tem conflitos nem no SLR: as reduções de S caem em eof e as de B em ↑, e os deslocamentos são em ↓ (ou ↑ onde não há redução).

Sem conflito no SLR ⇒ é SLR(1) ⇒ é LR(1). A coleção LR(1) tem os mesmos 11 estados: todo item de S tem lookahead eof e todo item de B tem ↑.

Produções vazias: reduzir S → ε desempilha 0 pares e consulta o goto no próprio topo.

Questão 1 · Lista 1 · Exercício 4

Não é LL(1), mas é LR(0) — logo LR(1)

Um parser LL(1) teria de escolher entre A e B ao ver “(”, sem saber quantos “(” virão antes de “)” ou “}”. O LR adia a decisão até o fim.

Por extenso: Reconhecer depois pode ser mais fácil que escolher antes

Em palavras

Nesta gramática, tanto A quanto B podem começar com (. Um parser LL(1) tentando escolher uma dessas alternativas só pelo próximo token encontra a mesma informação nas duas. O LR pode ler o prefixo comum sem abandonar nenhuma possibilidade.

Os itens do estado registram essas possibilidades até que os tokens seguintes as diferenciem. A escolha da redução acontece quando há informação suficiente no trecho reconhecido.

Exemplo, passo a passo

Em ( ( a ) ), o a permite reconhecer a alternativa de A; os fechamentos ) completam as camadas de A. Para a alternativa de B, o centro é b e os fechamentos são }.

O estado após ( ainda contém as possibilidades de A e B. Isso não é, por si, um conflito: a tabela só terá problema se uma mesma célula pedir duas ações diferentes.

Não confunda

“Não é LL(1)” é uma classificação desta gramática, não uma prova de que a linguagem é impossível de analisar. E LR(0) não significa “não olhar a entrada”: o parser consulta o token; o zero descreve a ausência de lookahead nos itens.

Gramática aumentada

r0: Goal → Start    r1: Start → A    r2: Start → B
r3: A → ( A )       r4: A → a
r5: B → ( B }       r6: B → b

CC₄ = goto(CC₀, “(”) guarda as duas possibilidades ao mesmo tempo: {A → ( • A ), B → ( • B }} mais o closure. Por isso não é preciso decidir cedo.

A prova

No LR(0), todo estado com item completo tem só aquele item (CC₂, CC₃, CC₅, CC₆, CC₉, CC₁₀). Nenhuma célula tem duas ações ⇒ LR(0) ⇒ LR(1).

Para treinar LALR: o LR(1) dessa gramática tem 18 estados (após “(” os lookaheads viram “)” e “}”), e a fusão LALR volta a 11.

Em palavras

Use a bancada como conferência da sua construção. Primeiro identifique o método, a produção aumentada e as produções numeradas. Depois compare os itens e as transições do seu desenho com os do simulador.

Exemplo, passo a passo

Não confunda

Um exemplo de entrada aceito não prova que toda a tabela está livre de conflitos. A classificação LR depende da coleção e da tabela completas. Também não resolva um conflito escolhendo arbitrariamente uma ação: isso esconderia a evidência pedida na prova.

Questão 2 · Framework de anotação da gramática

Atributos que sobem e atributos que descem

Uma SDD (definição dirigida por sintaxe) associa atributos aos símbolos e regras às produções. Uma SDT (tradução dirigida por sintaxe) insere trechos de código nas produções. A lista permite misturar as duas.

Por extenso: Anotar a árvore é fazer os nós trocarem informações

Em palavras

Um atributo é uma informação associada a uma ocorrência de símbolo na árvore. “Sintetizado” significa que o nó calcula algo a partir das informações de seus filhos e entrega o resultado para cima. “Herdado” significa que ele recebe o contexto necessário do pai ou de irmãos, conforme as regras.

Em List → List₁ Bit, List é o pai, List₁ é a lista restante à esquerda e Bit é o bit mais à direita. List₁.pos := List.pos + 1 manda uma posição maior para a esquerda; List.val := List₁.val + Bit.val reúne os valores calculados pelos filhos.

Exemplo, passo a passo

Para −101, o bit mais à direita ocupa a posição 0 e vale 1 × 2⁰ = 1. O bit do meio ocupa a posição 1 e vale 0. O da esquerda ocupa a posição 2 e vale 1 × 2² = 4.

As posições são transmitidas aos nós; os valores 4, 0 e 1 são somados até produzir 5. Sign.neg informa que o sinal é negativo, então Number.val fica −5.

Não confunda

O subscrito em List₁ identifica outra ocorrência de List na produção, não o valor 1. E .pos aqui é a posição que determina uma potência de 2; .val é o valor numérico calculado.

Sintetizado

Calculado a partir dos filhos, do próprio nó ou de constantes: informação que sobe. Regras que definem atributos do símbolo à esquerda criam sintetizados.

Exemplos: .val, .neg, .node, .str, .type.

Herdado

Vem do pai ou dos irmãos: informação que desce. Regras que definem atributos de símbolos à direita criam herdados.

Exemplo: .pos do número binário (e o ambiente de tipos).

Notação

Em E → E₁ + T, o E da esquerda é o nó pai e E₁ é a outra ocorrência de E, no lado direito. São nós diferentes, com atributos diferentes.

Exemplo do quadro: número binário com sinal

Construindo a AST nas reduções

O parser ascendente executa a ação de uma produção no momento em que a reduz. Por isso a árvore nasce das folhas para a raiz.

Por extenso: Como as ações de redução montam a AST

Em palavras

Leia E.node := mkNodePlus(E₁.node, T.node) assim: “crie um nó de soma, ligue nele as árvores que representam os dois operandos e guarde esse novo nó como a representação de E”. Os filhos já estão disponíveis quando essa redução acontece.

Já E.node := T.node significa apenas “use a mesma árvore que T já construiu”. Não se cria uma caixinha E a mais na AST.

Exemplo, passo a passo

Para 1 − (3 + 2), primeiro surgem as folhas 1, 3 e 2. Ao reconhecer 3 + 2, crie Plus com as folhas 3 e 2. Os parênteses repassam esse mesmo nó. Por fim, crie Minus com 1 à esquerda e Plus à direita.

O resultado é Minus(Int(1), Plus(Int(3), Int(2))). A soma fica dentro da subtração porque era o agrupamento determinado pelos parênteses.

Não confunda

AST e árvore concreta não são a mesma coisa. A árvore concreta guarda as produções e seus símbolos; a AST preserva as operações relevantes. Os parênteses podem desaparecer como nós sem perder seu efeito sobre o agrupamento.

ProduçãoAção
E → E₁ + TE.node := mkNodePlus(E₁.node, T.node)
E → E₁ − TE.node := mkNodeMinus(E₁.node, T.node)
E → TE.node := T.node
T → ( E )T.node := E.node
T → intLitT.node := mkNodeInt(intLit.val)
T → floatLitT.node := mkNodeFloat(floatLit.val)

As produções de repasse (E → T, T → ( E )) não criam nó: copiam o ponteiro. Os parênteses somem da AST, mas a forma da árvore (Plus embaixo de Minus) guarda a precedência que eles impunham.

Questão 2 · Lista 2 · Exercício 2

Interpretador com .str, .type e .val

Três atributos sintetizados por símbolo. A conversão de tipos acontece na operação: se um lado é float, o resultado é float e o outro lado é convertido com cast.

Por extenso: Uma mesma redução produz texto, tipo e valor

Em palavras

.str guarda como escrever a expressão; .type guarda a categoria do resultado; .val guarda o resultado numérico. Esses atributos respondem a perguntas diferentes e são calculados juntos a partir dos filhos.

Leia cast(E.type, E₁.val) assim: “converta o valor do operando esquerdo para o tipo que foi escolhido para a operação”. Primeiro se decide o tipo; depois se calcula com operandos compatíveis.

Exemplo, passo a passo

Em 3.5 + 2, um operando é float e o outro é int. A soma é float: converta 2 para 2.0 e obtenha 5.5. Em 1 − (3.5 + 2), a expressão interna é float, então a subtração também é float e vale −4.5.

A string construída é (1 - (3.5 + 2)). A regra de soma já colocou parênteses em torno de 3.5 + 2; a regra T → ( E ) repassa essa string para não repetir os parênteses na saída pedida.

Não confunda

Essa promoção int/float pertence ao interpretador deste exercício. Não a aplique automaticamente às regras de aritmética de COOL, que, no slide de referência, exigem dois Int. Tipo não é sinônimo de valor: −4.5 é valor; float é tipo.

Start → E { println(E.str + " = " + E.val) }

E → E₁ + T {
    E.str  := "(" + E₁.str + " + " + T.str + ")"
    E.type := float se E₁.type = float ou T.type = float
              senão int
    E.val  := cast(E.type, E₁.val) + cast(E.type, T.val)
}
E → E₁ − T { igual, com − }
E → T      { E.str := T.str; E.type := T.type; E.val := T.val }

Detalhe do gabarito: ele escreve T.str := "(" + E.str + ")" em T → ( E ). Como E → E₁ + T já parentiza, o resultado seria “(1 - ((3.5 + 2)))”. Para chegar à saída pedida, “(1 - (3.5 + 2)) = -4.5”, T → ( E ) só repassa.

A versão alternativa do gabarito imprime aos poucos: E → E₁ + { print(" + ") } T, T → ( { print("(") } E ) { print(")") } etc.

Questão 2 · Lista 2 · Exercício 3

Resolver a ambiguidade de a(i) na análise semântica

Em Fortran 77, a(i) pode ser chamada de função ou acesso a array. Em vez de o léxico consultar o sintático (como no typedef de C), o parser aceita a forma única e a análise semântica decide.

Por extenso: A sintaxe reconhece a forma; a declaração dá o significado

Em palavras

O texto a(i) tem a mesma forma visual em dois usos possíveis. Só a pontuação não informa se a é uma função ou um array. O parser pode construir um nó genérico com o nome a e a lista de expressões entre parênteses.

A análise semântica consulta a declaração de a. Se a for função, verifica os parâmetros e usa o tipo de retorno. Se for array, verifica as dimensões e os índices e usa o tipo do elemento.

Exemplo, passo a passo

Se a foi declarada como função que recebe Int e devolve Float, a(2) é uma chamada de tipo Float. Se a foi declarada como array unidimensional de Int, a mesma forma a(2) é um acesso a elemento de tipo Int.

Se a for um inteiro escalar, os parênteses não o transformam em função ou array: há erro semântico. Se a não estiver declarada, registre esse erro em vez de adivinhar seu papel.

Não confunda

Reconhecer uma sequência pela gramática não garante que ela tenha significado válido. Neste exercício, a solução é adiar a decisão para a tabela de símbolos, não inventar uma regra sintática diferente para cada declaração possível.

Como fazer

  1. A gramática produz um nó genérico: Start → name ( ExprList ) { Start.node := mkApply(name.lexeme, ExprList.nodes) }.
  2. Na análise semântica, lookup(name) na tabela de símbolos devolve a declaração.
  3. Conforme o tipo da entrada (função, array, outro, inexistente), o nó é reescrito ou anotado e verificado.

Verificações

  • Função: quantidade e tipos dos argumentos; tipo = retorno.
  • Array: quantidade de índices = dimensões; índices inteiros; tipo = elemento.
  • Outro / não declarado: reporta erro e continua.
Questão 2 · Lista 2 · Exercício 4 (a) e (b)

9 + 5 * 2 ⇒ “9 5 2 * +” e “+ 9 * 5 2”

Dois atributos sintetizados de string. A única diferença é onde o operador entra na concatenação: no fim (pós-fixa) ou no começo (prefixa).

Por extenso: Trocar a ordem do operador sem trocar a árvore

Em palavras

Na pós-fixa, cada operação escreve primeiro seus dois operandos e só depois o operador. Na prefixa, escreve primeiro o operador e depois os dois operandos. O agrupamento da expressão continua o mesmo.

Leia E.pos := fmt("%s %s +", E₁.pos, T.pos) como “junte a tradução pós-fixa do lado esquerdo, a do lado direito e, no fim, o sinal de soma”. Os espaços separam os tokens.

Exemplo, passo a passo

Em 9 + 5 * 2, a multiplicação é uma subexpressão: sua pós-fixa é 5 2 * e sua prefixa é * 5 2. Trate cada uma como um bloco ao montar a soma.

A pós-fixa completa fica 9 5 2 * +. A prefixa completa fica + 9 * 5 2. Não é só mover todos os sinais para o início ou para o fim: a ordem vem da estrutura da árvore.

Não confunda

Aqui .pos é a string pós-fixa, não a posição do bit usada no exercício binário. E a árvore pedida neste item é concreta: E, T e F continuam aparecendo, mesmo nas produções que apenas repassam os atributos.

Questão 2 · Lista 2 · Exercício 4 (c)

Traduzir só com print(…), sem atributos: dá em um passe?

Por extenso: Por que imprimir cedo demais pode ser irreversível

Em palavras

Uma chamada de print envia texto para a saída; depois não dá para inserir um operador antes do que já foi impresso. Na pós-fixa, isso combina com as reduções: quando uma operação é reconhecida, seus operandos já foram impressos e o operador pode sair por último.

Na prefixa, o operador precisa sair antes dos operandos. Com essas restrições — um passe, impressão imediata e sem guardar a expressão — falta informação no momento em que os primeiros operandos são lidos.

Exemplo, passo a passo

Ao começar pelo token 9, a entrada ainda pode ser apenas 9, ou 9 * 5, ou 9 + 5 * 2. As saídas prefixas começariam respectivamente por 9, * ou +. Imprimir 9 imediatamente já impediria as duas últimas saídas corretas.

Guardando uma árvore, o problema desaparece: depois de montá-la, visite primeiro a raiz, depois o filho esquerdo e depois o direito. A raiz + é impressa antes de 9 e da subárvore de multiplicação.

Não confunda

Não conclua que gerar prefixa é impossível. A impossibilidade discutida é a da estratégia restrita de impressão imediata sem armazenamento. Usar .pre ou guardar a AST muda essas condições e resolve o problema.

Pós-fixa: sim

E → E₁ + T  { print("+") }
E → T       { }
T → T₁ * F  { print("*") }
T → F       { }
F → intLit  { print(intLit.lexeme) }

A ação fica no fim da produção e roda na redução, quando os operandos já foram impressos. É o que o quadro mostra.

Prefixa: não, em um passe

E → { print("+") } E₁ + T
T → { print("*") } T₁ * F
F → intLit { print(intLit.lexeme) }

Para imprimir “+” antes do 9, o tradutor teria de saber, ao começar a ler 9, que haverá um + mais adiante — e quantos operadores virão (9 ⇒ “9”; 9 * 5 ⇒ “* 9 5”; 9 + 5 * 2 ⇒ “+ 9 * 5 2”). Essa informação pode estar arbitrariamente longe.

Além disso a gramática tem recursão à esquerda (não serve para descendente); eliminar a recursão não resolve a antecipação. É o Exemplo 5.16 do Dragon Book.

Solução: guardar a string em .pre (item b) ou montar a árvore e imprimir em pré-ordem depois.

Questão 2 · Escopo · Lista 2 · Exercício 5

Um nó Let com quatro filhos

Em vez de lets aninhados (um por declaração), o let “horizontal” vira um nó só: três declarações e a expressão final.

Por extenso: O nome local não existe antes da própria declaração

Em palavras

O let horizontal reúne várias declarações num nó da árvore, mas elas não passam a valer todas ao mesmo tempo. Cada inicializador é analisado com as declarações anteriores; só depois a nova variável fica disponível.

Um nome já existente no escopo externo pode ser usado no inicializador. Portanto, “a nova variável ainda não existe” não significa que qualquer uso desse nome seja sempre inválido: pode haver uma declaração externa visível.

Exemplo, passo a passo

Em x : Int <- z, o z local ainda não foi introduzido. A busca encontra o atributo z : String, que não combina com o Int declarado para x.

No inicializador de y, há um let interno: depois de analisar 5, seu y interno vale no corpo y + w. Esse y não é o y externo em declaração. Ao sair do let interno, volta-se ao escopo externo. Mais tarde, z : Int passa a esconder o atributo z : String no corpo final.

Não confunda

O formato horizontal da AST não altera a ordem de visibilidade. Um único nó com vários filhos não significa declarações simultâneas. O escopo é determinado pelo texto e pelas regras da linguagem, não pela ordem das chamadas durante uma execução.

class Main inherits IO {
  z : String <- "A";
  main() : Object {
    let x : Int <- z,
        y : Int <- (let y : Int <- 5 in y + w),
        z : Int <- 10
    in out_string(x + y + z)
  };
};

Índices de explicação: z₀ é o atributo; x₁, y₁, z₁ são as variáveis do let externo; y₂ é o y do let interno.

Escopo estático (léxico)

Um uso se refere à ligação mais próxima no texto do programa. (Escopo dinâmico usaria a ligação mais recente na execução.) COOL usa escopo estático.

Regra de visibilidade do let

As declarações são processadas da esquerda para a direita: o inicializador de cada uma é analisado antes de a variável existir; as anteriores já são visíveis.

Logo o z em x : Int <- z é o atributo z₀ : String — o z local ainda não existe.

A AST (formato do quadro)

x + y + z é associativo à esquerda: Plus(Plus(x, y), z). A chamada sem receptor vira Call com receptor self.

Questão 2 · Lista 2 · Exercício 6

Percorrendo a AST com uma pilha espaguete de tabelas

Cada escopo é uma tabela com ponteiro para a anterior. O caminho de qualquer tabela até a raiz é uma pilha. lookup sobe por esse caminho; achou ⇒ grava use no nó; não achou ⇒ reporta e continua.

Por extenso: Como seguir a trilha das tabelas de símbolos

Em palavras

Imagine cada tabela como uma folha com as declarações de um escopo e uma seta para a folha do escopo externo. Ao procurar um nome, examine a folha atual; se ele não estiver ali, siga a seta. A primeira declaração encontrada é a que vale.

Ao entrar num let, crie seu escopo. Para cada declaração, visite primeiro o inicializador e só depois insira a entrada. Ao sair, volte para a tabela externa; as entradas ainda referenciadas pela AST continuam existindo.

Exemplo, passo a passo

Quando o simulador visita o z usado para inicializar x, ainda não existe z local. A busca sobe até a tabela da classe e grava no nó um ponteiro use para o atributo z : String.

Ao visitar y dentro do let interno, encontra o y interno logo no escopo mais próximo. Ao visitar w, não encontra declaração em nenhuma tabela do caminho e registra erro. A busca não visita escopos irmãos nem declarações que serão inseridas no futuro.

Não confunda

“Pilha espaguete” descreve o encadeamento persistente de escopos, não uma lista única em que todos os nomes ficam visíveis. Sair do escopo muda a tabela ativa; apagar uma entrada que ainda é alvo de use deixaria a AST com uma referência inválida.

Questão 2 · Lista 2 · Exercício 6 (responda)

Por que anotar cada uso com a entrada da tabela?

Resposta

Porque o significado de um nome depende do ponto do programa, e a tabela muda depois desse ponto. Gravar use → entrada no momento do lookup congela a ligação certa; as fases seguintes (tipos, geração de código) leem o tipo e o endereço direto da entrada, sem refazer buscas.

Sem isso, uma fase posterior que repetisse lookup("z") a partir da tabela do let — já com x₁, y₁ e z₁ inseridos — acharia z₁ : Int para o z do inicializador de x. O uso passaria a ser Int e o erro String ≤ Int desapareceria.

E a persistência?

As tabelas não são apagadas no exit_scope: o use do y interno aponta para y₂, que mora em S_Let2. Se S_Let2 fosse descartada, o ponteiro ficaria pendurado.

Também é por isso que y₁ e y₂ são entradas diferentes, mesmo com o mesmo nome.

Checklist e armadilhas

Tradução dirigida por sintaxe

  • Diga quais atributos existem e se são sintetizados ou herdados.
  • Escreva uma ação por produção, inclusive as de repasse (E → T, T → F, T → ( E )).

  • Pós-fixa com print no fim da produção funciona em um passe; prefixa com print no começo, não.

Escopo e tabela de símbolos

  • enter_scope em classe, método e let; exit_scope no fim, sem apagar a tabela.
  • No let: analise o inicializador antes de inserir a variável.
  • lookup sobe pelos pais; o primeiro que achar vence (sombreamento).
  • Não achou: reporte e continue.
  • Anote use → entrada em cada nó Object.
Questão 3 · Inferência de tipos

Como ler uma regra de inferência

Premissas em cima, conclusão embaixo: se tudo acima da linha vale, vale o que está abaixo. É a mesma forma de “p → q, q → r ∴ p → r”.

Por extenso: Lendo os símbolos como uma frase inteira

Em palavras

Leia O, M, C ⊢ e : T assim: “usando o ambiente das variáveis O, as assinaturas dos métodos M e a classe atual C, podemos demonstrar que a expressão e tem tipo T”. O é uma letra, não o algarismo zero; os ambientes não estão sendo multiplicados.

Na regra Var: “se a consulta O(x) informa o tipo T para x, então x tem tipo T nesse contexto”. A parte de cima é o que preciso verificar; a parte de baixo é o que posso concluir se as verificações derem certo.

Exemplo, passo a passo

Se O(x) = Int, a conclusão é x : Int. Leia a segunda regra como: “se e₁ é inteiro e e₂ é de ponto flutuante, então a soma tem tipo de ponto flutuante”, segundo a regra ilustrada.

Em O[Int/x], leia “o ambiente O, agora com x associado a Int”. Essa operação descreve informação de tipos; não atribui o valor Int a uma variável durante a execução.

Não confunda

O sinal : significa “tem tipo”, não “recebe valor”. E a soma Int/Float deste exemplo ilustra a notação: não substitui a regra específica de aritmética de COOL, que exige dois operandos Int no slide de referência.

Os ambientes de COOL

  • O (objetos): O(x) = T diz que, no ambiente O, o identificador x tem tipo T.
  • M (métodos): M(C, m) = (T₁, …, Tₙ, T_R) diz que a classe C tem m(x₁ : T₁, …, xₙ : Tₙ) : T_R.
  • C: a classe atual (para SELF_TYPE).
  • O[T/x]: O com x atualizado para o tipo T (esconde um x anterior).

Contexto e julgamento

O, M, C ⊢ e : T

“No contexto O, M, C, a expressão e tem tipo T.” O, M, C é o contexto; e : T é o julgamento.

Como usar na prova: escreva a regra do nó principal com os tipos desconhecidos como incógnitas (T₁′, T₂′…). Depois visite os filhos, descubra cada tipo e preencha as premissas. É o movimento do gabarito do Ex. 7.

Questão 3 · Subtipagem

A ≤ B é uma ordem parcial; A ⊔ B é o menor tipo acima dos dois

Por extenso: O if precisa de um tipo que sirva para qualquer ramo

Em palavras

Leia B ≤ A como “B é subtipo de A: um objeto de B pode ser usado onde se espera A”. A direção não se inverte automaticamente. Duas classes podem não ser subtipos uma da outra; por isso a ordem é parcial.

Leia D ⊔ C como “o tipo mais específico que aceita tanto D quanto C”. Na árvore de herança simples mostrada, suba a partir dos dois tipos e encontre o primeiro ancestral comum.

Exemplo, passo a passo

D sobe para B, depois A e Object. C sobe para A e Object. O ancestral comum mais próximo é A, então D ⊔ C = A.

Leia if e₀ then (e₁ : D) else (e₂ : C) fi : A assim: “se a condição e₀ for verdadeira, o resultado vem de e₁ e tem tipo D; caso contrário, vem de e₂ e tem tipo C. Como ambos cabem em A, o if inteiro recebe o tipo estático A”. A condição precisa ser Bool.

Não confunda

O resultado não precisa ser Bool só porque a condição é Bool. A é o tipo garantido estaticamente; em execução, o objeto produzido continua sendo o do ramo escolhido, sem ser transformado num objeto de classe A.

Object também aceitaria os dois ramos, mas não é a melhor resposta quando A é um ancestral comum mais específico. Se um tipo já é subtipo do outro, como D ≤ B, então D ⊔ B = B.

≤ (do quadro)

  • A ≤ A para todo tipo A (reflexividade).
  • Se B herda de A, então B ≤ A.
  • Se A ≤ B e B ≤ C, então A ≤ C (transitividade).
  • SELF_TYPE em C: se C ≤ D, então SELF_TYPE_C ≤ D.

⊔ (join, menor limitante superior)

A ⊔ B = C se, e somente se:

  • A ≤ C e B ≤ C (C é limitante superior);
  • para todo D, (A ≤ D ∧ B ≤ D) ⇒ C ≤ D (é o menor).

SELF_TYPE_C ⊔ A = C ⊔ A. Usado no if: o tipo é T₁ ⊔ T₂.

Questão 3 · Referência

As regras de inferência vistas em aula

Toque em um cartão para ver a regra por extenso; toque novamente para voltar à fórmula. Use os botões para navegar também pelo teclado.

Literais

O tipo de um literal vem do próprio valor escrito no programa: um número inteiro é Int; true e false são Bool. Para os booleanos, não é preciso consultar nenhuma variável.

Exemplo: 42 : Int e true : Bool. A conclusão é direta, sem outras premissas.

Variável

Se o ambiente de tipos O registra que a variável x tem tipo T, podemos concluir que x é do tipo T no contexto atual.

Exemplo: se O(x) = Int, então x : Int. Uma variável não declarada gera erro; NoType é usado apenas para recuperar a análise.

x sem declaração: erro; na recuperação, x : NoType.

Aritmética

Para somar, subtrair, multiplicar ou dividir, as duas expressões devem ser do tipo Int. Se ambas forem inteiras, o resultado também será Int; se não forem, há erro de tipos.

Exemplo: 2 + 3 : Int é válido; 2 + true é inválido. Esta regra não prevê conversão automática para Float.

typeCheck(e₀ op e₁)
  t₀ := typeCheck(e₀)
  t₁ := typeCheck(e₁)
  se t₀ = Int e t₁ = Int: retorne Int
  senão: retorne ERRO

New

A expressão new T₀ cria um objeto e recebe o tipo T₀. Quando T₀ é SELF_TYPE, o tipo é interpretado em relação à classe atual C, como SELF_TYPE_C.

Exemplo: new A : A. Já new SELF_TYPE acompanha a classe do objeto atual.

If

A condição e₀ deve ter tipo Bool. Se o ramo then tem tipo T₁ e o ramo else tem tipo T₂, o if inteiro recebe o menor supertipo comum: T₁ ⊔ T₂.

Exemplo: se B e C herdam de A, retornar new B num ramo e new C no outro faz o if ter tipo A, não Bool.

Let sem inicialização

Declare x com tipo T₀ no ambiente O e analise o corpo e nesse ambiente ampliado. O tipo do let completo é T₁, ou seja, o tipo do corpo.

Exemplo: let x : Int in x + 1 tem tipo Int. A variável x fica visível no corpo do let.

O[t/y]: atualiza o tipo associado a y no ambiente O para t.

Let com inicialização

Primeiro analise o inicializador e₀ sem introduzir x no ambiente. Seu tipo T₂ deve ser subtipo do tipo declarado T₁ (resolvendo SELF_TYPE, se necessário). Depois declare x : T₁ e analise o corpo e₁: o resultado do let é T₃, tipo desse corpo.

Exemplo: let x : A <- new B in x é válido se B ≤ A; o tipo estático da expressão é A.

e₀ é tipado em O (sem x); e₁ em O[T₁/x]. Exemplo do quadro: let x : A <- new B vale porque B ≤ A.

type-check(let x : t₀ <- e₀ in e₁)
  t₁ := SELF_TYPE(C) se t₀ = SELF_TYPE senão t₀
  t₂ := type-check(e₀)
  se não (t₂ ≤ t₁): reporte "tipo de e₀ …"
  atualize a tabela com o tipo de x
  retorne type-check(e₁)

Despacho dinâmico

Determine o tipo do receptor e₀ e dos argumentos. Consulte em M a assinatura do método m para o tipo do receptor; cada argumento precisa ser compatível com o respectivo parâmetro. O resultado é o retorno declarado do método, ou o tipo do receptor se o retorno for SELF_TYPE.

Exemplo: em obj.m(a), a implementação executada depende da classe real de obj. Sem receptor explícito, usa-se self.

Se T₀ = SELF_TYPE_C, procura m em C. Sem receptor, e₀ é self.

Despacho estático

Em e₀@T.m(...), o tipo do receptor deve ser subtipo de T. O método é procurado especificamente na classe T e os argumentos devem respeitar seus parâmetros. O resultado segue o retorno declarado; se ele for SELF_TYPE, usa-se o tipo do receptor e₀.

Exemplo: se B herda de A, x@A.f() escolhe a implementação de f de A, mesmo quando x contém um objeto B.

x@A.f() usa o f de A mesmo que x seja um B.

Questão 3 · Lista 2 · Exercício 7

A regra do let horizontal, com os índices certos

Cada inicializador é tipado no ambiente produzido pelas declarações anteriores; depois o ambiente ganha a nova variável com o tipo declarado.

Por extenso: Um ambiente antes e outro depois de cada declaração

Em palavras

Leia Oᵢ ⊢ eᵢ : Tᵢ′ como “antes de inserir a variável i, analise seu inicializador e descubra o tipo que ele realmente tem”. Leia Tᵢ′ ≤ Tᵢ como “esse tipo encontrado precisa caber no tipo declarado”. O apóstrofo distingue encontrado de declarado; não é uma derivada.

Só depois forme Oᵢ₊₁ = Oᵢ[Tᵢ/xᵢ]: acrescente a variável com o tipo declarado. Ao fim das n declarações, o corpo é analisado em Oₙ₊₁, onde todas elas já estão disponíveis.

Exemplo, passo a passo

Em let x : A <- new B, y : A <- x in y, suponha B ≤ A. Primeiro, new B tem tipo B e B cabe em A. Insira x : A. Depois, o inicializador de y é x, cujo tipo estático é A; insira y : A. O corpo y tem tipo A, então o let inteiro tem tipo A.

Observe a ordem: o tipo de x no ambiente é A, não B. E o inicializador da nova variável não a enxerga, embora possa enxergar uma declaração externa com o mesmo nome.

Não confunda

O tipo final do let vem do corpo após in, não necessariamente do último inicializador. Na recuperação de erros adotada pelo exercício, uma incompatibilidade é reportada, mas a declaração ainda é inserida com seu tipo declarado para permitir a análise do restante.

O₁ = O · Oi+1 = Oᵢ[Tᵢ/xᵢ] para 1 ≤ i ≤ n

Assim e₁ é visto em O₁ = O (sem x₁), e₂ em O₂ (com x₁), …, e o corpo em On+1 (com todos). É exatamente a numeração do exemplo do gabarito: O₁ ⊢ z, O₂ ⊢ (let y …), O₃ ⊢ 10, O₄ ⊢ out_string(…). A fórmula geral do gabarito escreve Oᵢ = Oᵢ₋₁[Tᵢ/xᵢ] com Oᵢ ⊢ eᵢ, o que colocaria xᵢ no próprio inicializador.

Procedimento

  1. Descubra o tipo Tᵢ′ do inicializador eᵢ no ambiente Oᵢ.
  2. Verifique Tᵢ′ ≤ Tᵢ.
  3. Acrescente xᵢ : Tᵢ ao ambiente (Oi+1).
  4. Repita; por fim, o tipo do corpo é o tipo do let.

Reportar e prosseguir

  • Tᵢ′ ≤ Tᵢ falhou: reporte e continue com Oi+1 = Oᵢ[Tᵢ/xᵢ] (o tipo declarado).
  • Identificador não declarado: reporte e dê NoType ao nó.
  • Qualquer operação com NoType resulta em NoType.
  • NoType ≤ T para todo T: nenhum erro em cascata por causa de um erro já reportado.
Questão 3 · Lista 2 · Exercício 7 (código do Ex. 5)

Preenchendo as incógnitas T₁′, T₂′, T₃′, T₄

Ambiente inicial: O tem z : String (o atributo); M tem out_string herdado de IO. Avance e veja a regra se completar e os erros aparecerem sem interromper a análise.

Por extenso: Três erros independentes, sem multiplicar mensagens em cascata

Em palavras

O objetivo do passo a passo é descobrir os tipos e registrar problemas sem parar no primeiro. O compilador continua a análise com as convenções de recuperação do exercício; isso não torna o programa válido.

NoType marca um resultado cujo tipo não pôde ser obtido por causa de um erro anterior. No exemplo, ele é propagado pela soma com w e aceito na comparação de compatibilidade para evitar mensagens redundantes.

Exemplo, passo a passo

Primeiro: o z que inicializa x é o atributo String. String ≤ Int falha, mas x entra no ambiente como Int. Segundo: w não foi declarado; y + w e o let interno recebem NoType. Não se repete esse mesmo problema como outro erro de inicialização de y.

Depois, z local recebe Int. No corpo, x, y e z têm os tipos declarados Int, então a soma tem tipo Int. Terceiro: out_string espera String, não Int. As incógnitas ficam T₁′ = String, T₂′ = NoType, T₃′ = Int; o retorno declarado conhecido permite conservar T₄ = SELF_TYPE_Main durante a recuperação.

Não confunda

“Consegui anotar um tipo depois de recuperar o erro” não significa “todas as premissas foram satisfeitas”. A chamada continua errada pelo argumento. NoType e a conservação do retorno conhecido são estratégias deste exercício, não permissões normais para executar um programa mal tipado.

Questão 3 · Lista 2 · Exercício 7 (exemplo sem erros)

O exemplo sem erros, premissa por premissa

let x : Int <- 10, y : Int <- (let y : Int <- 5 in y + 5), z : Int <- 10 in out_int(x + y + z). A mesma regra, agora com todas as premissas satisfeitas; o tipo final vem da assinatura de out_int.

Por extenso: O tipo da chamada não é o tipo do que ela imprime

Em palavras

Os três inicializadores são compatíveis com Int. No let interno, o y local vale no corpo y + 5; essa soma é Int e fornece um inicializador válido para o y externo. No corpo final, x + y + z também é Int.

A assinatura out_int(Int) : SELF_TYPE diz duas coisas diferentes: o argumento esperado é Int; o resultado devolvido pela chamada é self. O tipo do argumento não determina sozinho o tipo do retorno.

Exemplo, passo a passo

Com os valores deste exemplo, x recebe 10, o y interno recebe 5 e produz 5 + 5 = 10 para o y externo, e z recebe 10. Se executado, o corpo imprime 30.

Mas a chamada devolve self. Como o receptor implícito é self : SELF_TYPE_Main, a chamada tem tipo SELF_TYPE_Main. Esse também é o tipo do let completo, e ele é compatível com o retorno Object declarado para main.

Não confunda

Não conclua que o let tem tipo Int porque contém variáveis inteiras ou porque imprime 30. Siga o tipo da expressão depois de in. Aqui essa expressão é uma chamada de método cujo retorno é SELF_TYPE.

out_int(x : Int) : SELF_TYPE imprime e devolve self. Chamado em Main sem receptor, o receptor é self : SELF_TYPE_Main, então a chamada — e o let inteiro — tem tipo SELF_TYPE_Main, que é ≤ Object (tipo de retorno de main).

Q1 · Em CC₆ do Ex. 2 há [A → B C •, a] e [A → B C • f, a]. Há conflito?
Não. r2 vai para a coluna a; s8 vai para a coluna f. Células diferentes.
Q1 · Por que o Ex. 2 não é LR(0)?
O LR(0) põe r2 em todas as colunas de CC₆, inclusive f, onde já há s8: shift/reduce. O SLR resolve, porque FOLLOW(A) = {a}.
Q1 · Pilha (⊥,0)(B,3)(C,6)(f,8), entrada “a eof”, ação r3. O que acontece?
A → B C f tem 3 símbolos: desempilha 3 pares; topo exposto é 0; Goto[0, A] = 2; empilha (A,2). A entrada continua “a eof”.
Q1 · Qual o lookahead de [B → • b] em CC₀ do Ex. 2?
c. Vem de [A → • B C, a] e [A → • B C f, a]: FIRST(C a) = FIRST(C f a) = {c}.
Q1 · Quando a fusão LALR cria conflito?
Só reduce/reduce: dois estados LR(1) de mesmo núcleo cujos lookaheads, unidos, põem duas reduções na mesma coluna. Shift/reduce novo nunca aparece.
Q1 · Por que o Cmd do quadro não é SLR?
CC₂ tem Cmd → Lhs • = Rhs e Rhs → Lhs •. FOLLOW(Rhs) contém “=” (por Lhs → * Rhs e Cmd → Lhs = Rhs), então r5 cai na coluna “=” junto com s6. No LR(1) o item tem lookahead eof.
Q2 · List.pos no número binário é herdado ou sintetizado?
Herdado: vem do pai (List₁.pos := List.pos + 1; Bit.pos := List.pos).
Q2 · Por que T → ( E ) não cria nó na AST?
Parênteses só agrupam. A forma da árvore já guarda a precedência; a ação só repassa E.node.
Q2 · Em let x : Int <- z, …, z : Int <- 10 in …, qual z o inicializador de x usa?
O atributo z₀ : String. O z local só é inserido depois. Daí o erro String ≤ Int.

O ambiente O com x associado ao tipo T (esconde uma ligação anterior de x).
Q3 · B e C herdam de A; D herda de B. Tipo de if c then new D else new C fi?
D ⊔ C = A.
Q3 · Tipo de out_int(e) chamado dentro de Main, sem receptor?
SELF_TYPE_Main: a assinatura é out_int(Int) : SELF_TYPE, e o receptor implícito é self.
